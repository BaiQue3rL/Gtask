# 数据模型与同步不变量

## 支持范围

当前版本只允许以下游戏 ID：

| ID | 游戏 |
|---|---|
| `genshin` | 原神 |
| `star-rail` | 崩坏：星穹铁道 |
| `zenless` | 绝区零 |
| `wuthering-waves` | 鸣潮 |

渲染进程传入的游戏 ID 必须在主进程再次校验，不能依靠界面选项限制。

## 清单分类

| 分类 | 用途 |
|---|---|
| `main_quest` | 主线是否完成，不记录具体任务 |
| `side_quest` | 支线是否完成，不记录具体任务 |
| `limited_event` | 有结束时间的限时活动 |
| `permanent_event` | 用户维护的常驻活动 |
| `weekly` | 默认周一重置的周常事项 |
| `endgame` | 按游戏、模式和周期记录的深渊类玩法 |
| `exploration` | 地图区域及可选百分比 |
| `custom` | 任意用户事项 |

每款游戏首次初始化时只生成一条主线状态和一条支线状态。它们使用稳定 ID，软删除后不会因下次启动而重新出现。

主线和支线是按游戏版本维护的两个固定状态项。它们共享当前版本的 `versionKey` 和结束时间，并显示与其他版块一致的简洁“剩余 ××”倒计时，不显示“版本结束倒计时”等额外前缀；版本结束后自动恢复为未完成。版本时间来自全局公开资料同步或任务版块“版更校时”，并保存明确服务器时区，不能按固定版本天数猜测。“版更校时”只校正版本键与版本开始/结束时间，不增删任务，也不直接改写完成状态。

## 来源与完成状态

`source` 有三种取值：

- `manual`：纯手动项目。
- `public_schedule`：公开资料，不含个人状态。
- `personal_sync`：登录后取得的个人数据。

用户手动完成事项时：

1. `completed` 设为 `1`。
2. `completed_at` 记录首次完成时间，用于本周统计。
3. `manual_completion_locked` 设为 `1`。
4. 当前周期内的远端同步不得把它改回未完成。

用户主动改回未完成时，清除 `completed_at` 和 `manual_completion_locked`。

## 删除语义

界面删除只将 `archived` 设为 `1`，不执行物理删除。这样可以：

- 防止同步失败误删历史数据。
- 防止有 `remote_key` 的远端事项被下一次同步立即重新创建。
- 为以后提供回收站或恢复功能保留空间。

除固定的“任务”版块外，其余可维护版块必须提供“一键删除已完成”操作，并遵守：

- 只处理当前选中游戏、当前版块内已完成的事项。
- “任务”版块固定为主线和支线，不提供删除按钮；“活动”包含限时和常驻活动；“周期事项”包含周常和深渊/挑战模式；“地图探索”和“自定义清单”各自独立。
- 不受“只看未完成”等当前筛选条件影响，作用范围始终是整个版块。
- 执行前显示一次包含删除数量和版块名称的确认提示。
- 批量操作仍采用软删除，不影响其他版块，也不物理删除历史记录。
- 同步适配器不得因为远端仍存在对应项目，就自动恢复用户批量删除的事项。

## 信息颗粒度与来源分工

### 活动

一条清单对应一个有独立名称的活动：

- 限时活动保存名称、开始时间、结束时间、倒计时、来源和可选的个人完成状态。
- 常驻活动默认由用户手动维护；公开来源可以建议新增，但不能擅自删除或覆盖手动记录。
- 活动时间优先来自官方公告或可验证的公开资料；社区资料图只能作为辅助来源，需要保存来源和抓取时间。
- 登录后的个人接口只负责补充账号可用的参与/完成状态，不能替代公开资料。
- 活动卡片可以显示一个或多个轻量“玩法标签”，例如签到、战斗、战棋、射击、跑酷、解谜、音游、经营、肉鸽或剧情；标签只用于筛选和辅助理解，不新增版块，也不替代限时/常驻分类。
- 玩法标签由 Codex 结合中文官方名称、玩法说明和可验证来源给出；标签允许后续扩展，本地程序只校验数量、长度和结构，不按标题关键词猜测。Codex 会主动补齐旧活动标签，交叉核验后仍无法确认时使用“未知”，禁止写入“待识别”。

### 周期事项

一条清单对应一个可独立判断完成状态和周期的玩法或事项：

- 普通周常默认每周一重置。
- 深渊类玩法按“游戏 + 模式”分开，例如深境螺旋、幻想真境剧诗、式舆防卫战和危局强袭战各自独立。
- 每期挑战使用独立的周期键和远端键；新一期新增清单，不重置或改写已完成旧期。
- 保存周期键、开始/结束时间、倒计时、完成状态、数据来源和最后成功同步时间。
- 个人完成状态优先来自登录后的战绩接口；公开资料只提供周期时间，不能假设用户已经完成。
- 深渊/挑战的统一产品语义是“本期有有效个人挑战记录即完成”；不要求满星、最高难度、全部奖励或最终层。只有个人接口明确表示本期完全没有挑战记录时才写未完成。
- “是否存在战绩”必须按每个官方接口已验证的确定性字段机械判断；字段含义不确定时进入 Codex 核验或保持原状态，不能猜测。

### 地图探索

一条清单对应官方个人数据能够稳定识别的区域单位，并允许用户继续细分：

- 保存区域名称、可选上级区域、探索百分比、完成状态、来源和最后成功同步时间。
- 登录后的个人战绩负责提供账号可见的区域探索度。
- 用户手动创建的子区域或待办不能被同步删除。
- 远端暂时缺少旧区域时保留本地最后成功数据，并标记为过期，而不是删除。

### 来源优先级

不同来源负责不同事实，不使用单一来源覆盖整条记录：

1. 用户手动修改和手动完成锁优先级最高。
2. 登录后的个人数据负责账号完成状态、战绩和探索百分比。
3. 官方公开资料负责活动名称、周期和开始/结束时间。
4. 社区排期图只作补充，需要用户确认或经过结构化校验。
5. 本地最后成功数据是同步失败时的兜底。

## 同步状态

每款游戏在 `sync_states` 中独立保存：

- 模式：`manual`、`public_schedule`、`personal_sync`。
- 状态：`idle`、`success`、`error`、`stale`、`verification_required`。
- 最后尝试时间、最后成功时间和说明信息。

## 同步模式与界面行为

每款游戏独立保存同步模式和自动同步范围。

### 刷新清单

“刷新清单”是立即执行的全局公开资料同步按钮，不再保留只有一个选项的下拉菜单。

任务、活动、周期事项和地图探索版块各自提供同步操作。任务版块只提供 `版更校时`，用于校正官方版本排期和倒计时，不提供个人 `同步进度`；活动、周期事项和地图探索的 `同步进度` 仅在当前游戏的个人接口确实提供该版块数据时显示。若当前版块规范清单为空或不完整，这一次“同步进度”会自动先补建公开规范清单，再合并个人进度。

个人数据平台按游戏自动确定：

- 原神、崩坏：星穹铁道、绝区零使用米游社。
- 鸣潮使用库街区。

### 全手动同步

软件不提供自动模式，启动时不会联网。用户每次手动选择“同步清单”或“同步进度”后，界面通过 IPC 请求对应协调器。离线时不运行 OCR 或其他自动识别，用户直接使用事项编辑器手动维护。

同步过程通过统一进度事件显示阶段、当前/总步骤、人工验证、重试和最后更新时间。公开资料任务把进度持久化到 SQLite，桌面端轮询恢复；个人数据适配器通过 IPC 实时上报。超过 30 秒没有更新时界面显示停滞提示，但不会擅自取消或丢弃旧数据。

公开资料任务在 Codex 领取前只能观测“已排队/尚未接单”。Codex 自身在 MCP 可用前发生的 WebSocket 或启动重试不对应用暴露，因此界面会说明“仍在启动或连接，内部重试次数暂不可见”，不得按等待时间伪造 `1/5`。领取任务后由 Codex 回传的重试次数才作为真实进度显示。

同步解析遵循严格职责边界：本地代码只处理结果唯一且可验证的机械转换；名称、分类、状态含义、自然语言时间、来源时区等语义问题必须交给 Codex。Codex 不可用或置信度不足时保持待核验，不允许本地规则猜测写入。

右上角记录最后一次成功的全局清单同步；活动、周期事项和地图探索分别记录本版块最后一次成功同步。版块同步不会把全局状态改成“已同步”，全局同步成功会同时更新三个版块的时间。

同步适配器后续必须使用事务更新，并遵守：

- 不删除手动项目。
- 不覆盖当前周期内的手动完成锁。
- 请求失败时保留最后一次成功数据。
- 远端缺少旧地图或旧活动时不直接删除本地记录。

所有使用结束时间的版块采用统一预警语义：以转换后的绝对时间计算剩余时长，严格小于 72 小时时将“剩余 ××”显示为红色；等于或大于 72 小时不标红。尚未开始事项的“距离开始 ××”不属于临近结束预警。

## 数据库版本

- v1：游戏、清单、同步状态和远端身份索引。
- v2：增加 `completed_at`，用于本周完成统计。
- v3：增加每游戏的 `run_mode`、`auto_scope` 和最近一次同步范围。
- v4：增加 `schedule_kind`、周重置日、时区和挑战模式标识。
- v5：增加地图探索的可选上级区域。
- v6：增加同步事项的来源 URL，支持公开资料追溯。
- v7：增加 AI 资料 Agent 心跳和一次性公开资料任务队列，保存领取、完成、失败及证据状态。
- v8：增加版块级同步目标和用户显示时区。
- v9：增加挑战玩法自动周期规则兼容字段。
- v10：停用挑战自动重置并清空旧自动周期规则，仅保留周常自动重置。
- v14：任务版块加入当前版本时间校正、到期重置和独立同步状态。
- v15：活动事项加入轻量多玩法标签；旧数据默认无标签，个人进度同步保留公开资料已有标签。

数据库启动时开启外键约束和 WAL。后续结构变化必须新增迁移版本，不能直接假定用户数据库是空库。

## 当前同步合并实现

- 适配器必须输出规范化远端标识、分类和标题；时间、进度、周期等字段可选。
- 同一次批次在事务中合并，任一事项非法时整批回滚。
- 公开资料和个人数据使用同一规范远端标识时合并为同一事项。
- 公开资料不修改完成状态；个人数据可补充完成状态和探索进度。
- 当前周期的 `manual_completion_locked` 优先于远端未完成状态。
- 周常的 `period_key` 变化时重置本周完成状态和手动完成锁；挑战玩法的 `period_key` 变化时新增独立事项并保留旧期。
- 远端本次未返回的本地事项不会被删除；已经软删除的远端事项也不会自动复活。
- 上次成功同步超过 24 小时后只把同步状态标成 `stale`，仍保留数据和成功时间。

## AI 公开资料桥接

- 只有最近五分钟内登记过联网搜索能力的 Agent 才视为已连接；未连接时刷新按钮不可用。
- 点击刷新只创建指定游戏和同步范围的一次性任务，不直接向数据库写入 AI 文本。
- Agent 必须先领取任务，再通过专用 MCP 工具提交严格结构化排期和来源证据。
- 专用工具不接受 `completed`、探索进度、删除或凭据字段；公开资料永远不能改变用户完成状态。
- 提交仍调用事务化 `public_schedule` 合并器，因此不会删除手动项目、恢复归档项目或绕过手动完成锁。
