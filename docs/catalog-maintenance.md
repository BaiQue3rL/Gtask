# 公共清单维护标准

自 Gtask 1.2.0 起支持本文的维护能力。旧版客户端能力须单独核对；协议 v2 清单不能直接交给仅支持 v1 的客户端。

## 职责和唯一维护入口

Gtask 读取公共清单并按类型显示；个人接口由软件确定性地解析，只更新唯一匹配条目的完成状态或探索度。Codex 核验公共事实，程序批量编译、校验和应用。日常启动、显示、换期和个人同步不等待 Codex。

新公共事实统一维护在累计的 `updates/catalog.json`。应用构建直接嵌入该文件，远程更新也读取该文件；历史 TypeScript 种子只负责首发存量和旧库兼容，不再要求每次活动、地图或规则维护重复编辑一份源码。稳定键和已有退役记录必须保留。

## 操作流程

1. 确定游戏与范围。`pnpm build` 后，`pnpm catalog:check --inventory` 用隔离内存库列出完整公共目录、规则和缺时间复核项，不访问玩家库、不输出个人进度。已有 MCP 任务还应读取脱敏观察与任务覆盖状态。
2. 枚举该范围内的新增、变化、漏项、跨版本活动及到期复核项；复用仍有效的来源。来源失败是未覆盖，不能写成无变化。完整核查不要求把未变条目全部重新搜索或提交。
3. Codex 一次写出核验后的差异 JSON，使用与公开清单相同的协议、较新的 `publishedAt` 和新的 `revision`。只含实际变动；不含个人字段。研究记录保留来源、未解决项和核查覆盖范围。
4. `pnpm catalog:check --base updates/catalog.json --delta <差异.json> --output <待审查清单.json>` 生成累计清单，并通过真实消费器校验。程序合并稳定键、保留旧退役、拒绝冲突；无变化不产生新修订。复核生成的差异后，将其作为仓库公开清单。
5. 运行相关回归和 `pnpm catalog:check`。发布按用户已有授权执行；提交、远端可读、镜像一致和客户端回执分别报告。具体软件版本未获批准时不改版本号或发布 Release。

直接维护仓库公共清单可完全离线于 Gtask 应用，不需要创建应用内研究任务。已有 MCP 任务仍精确领取 job ID，按实时契约批量写入并保留阶段状态；旧任务队列不是独立后台服务，不以退出应用后的空结果当作研究完成。

## 限时资格与缺时间例外

活动必须是官方独立命名的限时参与事项。常驻、永久玩法、长期一次性任务、卡池、商店、关卡和奖励档位不加入。没有时间本身不证明常驻或限时。

通常提供带时区的 `startsAt`、`endsAt`。协议 v2 可使用 `deadlineReview` 例外：`eligibility=confirmed_limited`、`openState=confirmed_open`，限时和当前开放的证据链接、已检查的 `checkedSources`、`checkedAt`、`reviewAt` 和 `missingReason` 均必填；`endsAt` 为空。`startsAt` 不知道时也可为空，不能把核查时刻冒充实际开放时刻。

界面显示“截止时间待确认”。`reviewAt` 只触发维护复核，不能自动删除活动。每次覆盖游戏时优先复核，版本切换时必须复核。补齐时限后保留同一稳定键和个人状态；确认结束、常驻，或开放依据失效且复核仍无法确认继续开放时，维护端明确发布移出主清单的决定并保留原因，不能让例外无限累积。

日期精度和“维护结束后”条件暂不伪装成精确时刻；未确认当前开放又不能表达开始边界的候选留在研究记录。协议 v1 客户端不支持缺时间例外，不能向旧客户端谎称已经升级。

## 周期规则与未来例外

协议 v2 的 `games[].scheduleUpdates` 支持四种有限数据结构；具体字段以 `src/main/published-schedules.ts` 的共享校验为准，不执行任何远程代码。

| kind | 用途 |
| --- | --- |
| `cycle_rule` | 稳定模式、规则生效边界和已支持的固定间隔、每月指定日、关联版本规则；cadence 与 duration 独立 |
| `cycle_window` | 某一期的官方例外；`nominalStartsAt` 标识原规则下的那一期，`periodKey` 保持身份，实际起止可以校正 |
| `version_window` | 当前或未来版本的例外；同样保留原开始边界与实际起止 |
| `version_rule` | 从明确边界起生效的版本 cadence |

记录使用稳定 `key`，纠错更新同一 key；撤回错误或取消的规则/例外使用 `scheduleArchives`，不能只从差异里省略。冲突窗口或同一生效边界的竞争规则拒绝整批应用。模式必须已有或同批明示新增，规则本身不会偷偷创建目录。

未来例外先持久保存；当前期仍有效时不覆盖当前完成状态。当前期到边界后显示下期开启时间，允许空窗；同一期校时保留完成和手动锁，真正换期保存历史并重置。常规换期无需逐期发布。当前一期改时使用 window，长期排期改变使用 rule；不要同时留下相互矛盾的旧窗口和规则。

## 地图、证据与恢复

地图仅 `region`/`subregion` 两级，收录前确认独立探索进度资格；改名与纠正父级沿用已发布稳定键。详见 `ai-map-catalog-maintenance.md`。当前个人快照的一级探索度优先于派生平均值。

所有公共更新、规则、例外、退役和接收回执在同一数据库事务中提交，失败全部回滚。旧内置数据不覆盖较新公共事实或复活退役项。备份保留公共回执与个人状态；清单维护不能清空数据库、凭据或用户自定义内容。
