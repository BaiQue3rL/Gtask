# Gtask 全功能审计与修复

日期：2026-09-14。范围：当前工作区源码、维护入口、隔离数据库与开发态 Electron。应用版本保持 1.1.1，数据库前向迁移至 schema v6；本轮没有修改正式玩家数据库、已安装程序或远端版本。

**结论：保留“软件读取统一清单、分发版块、自动同步个人进度”的架构。发现的问题主要位于进度证据、清单新旧优先级、跨期状态和退出保存，不需要把日常同步重新交给 Codex。**

> 后续可靠性与性能目标另有新增修复和维护实现，见 [目标验收记录](reliability-performance-goal.md)。本文的 v6、419 项测试及“尚未实施”是第一阶段历史结果；当前标准见 `catalog-maintenance.md` 和 `next-session.md`。

## 已修复的问题

| 优先级 | 触发条件与原来的问题 | 修复与验证 |
| --- | --- | --- |
| P1 | 个人接口缺少完成字段，被缺省零值解释为明确未完成 | 四游戏解析保留完成/未完成/未知三态；未知保留旧状态，明确无记录仍可纠正错误完成。解析与数据库回归通过 |
| P1 | 公共清单直接进入真正新一期，保留上一期完成和手动锁 | 保存旧期历史、清除完成/锁/绑定；同一期校时保留状态，未来一期不能覆盖当前活跃窗口，延迟旧窗口不能倒退当前期。边界回归通过 |
| P1 | 鸣潮深塔接口调整区域顺序，中间位置的侧塔被误认作手动挑战区域 | 使用已验证塔区名称，不按数组位置推定；缺嵌套字段保持未知。重排和不完整响应回归通过 |
| P1 | 包内清单在重启时覆盖已校正名称或周期时间；退役地图重新生成 | 独立公共核验时间和退役记录；启动补齐入口使用包内真实核验时间。文件库重开与 v5 迁移回归通过 |
| P1 | 恢复旧备份后，库外状态文件仍声称新清单已经应用；更新失败可能状态脱节 | 清单修订、发布时间、内容哈希与整批更新同事务，备份一并恢复；非法第二游戏使第一游戏写入和回执一起回滚。实际备份恢复回归通过 |
| P1 | 原神一级地图明确返回 0%，被子区平均值替换 | 保留当前个人快照的明确一级值，包括 0%；只有缺省一级值时才允许子区推导。地图与个人快照回归通过 |
| P1 | 退出/切换账号期间旧网络请求返回，仍可写入进度 | 返回后再次核对凭据并检查取消信号；失效请求丢弃。退出期间响应回归通过 |
| P1 | 档期观察非法导致同步报错，但此前的进度已经写入 | 进度、快照、绑定和脱敏观察进入同一事务；失败完整回滚。故障注入回归通过 |
| P1 | 设置修改后很快关闭，重启丢失设置 | 原退出流程立即强杀进程，浏览器存储没有落盘；现在先刷新存储并正常退出，5 秒未结束才兜底强制收尾。真实 Electron 测试先复现丢失，再验证修复 |
| P2 | 空窗期周期卡片受“隐藏未开始事项”设置影响消失 | 开关仅控制限时活动；周期显示下次开始倒计时，并拒绝向未来周期写入无日期的缓存战绩。显示与进度边界回归通过 |
| P2 | 镜像 revision 相同但内容不同，被当作相同清单；可访问的旧软件镜像遮住 GitHub 新版本 | 比较实际清单内容和回执哈希；自动选择时 GitHub 为权威。软件更新并行读取来源，避免串行等待累加。分歧和旧镜像回归通过 |
| P2 | 同游戏列表请求乱序覆盖新结果，跨游戏异步操作把项目插入错误列表 | 列表和回收站只接收最新请求；写入后刷新、检查游戏归属，恢复操作按 ID 去重。代码路径检查与界面 CRUD 回归通过，未声称对所有并发时序做穷举 |
| P2 | 维护领取省略 ID 可取到无关任务，领取空结果被旧 Skill 当作成功 | ID 必填；明确返回领取、恢复、占用、已结束、不存在等结果。精确领取及同任务恢复回归通过 |
| P2 | 本地 CLI/MCP 缺数据库参数时悄悄创建另一份库 | 要求显式数据库路径；清单校验则使用专用内存库，不需要玩家库。构建后的入口拒绝与隔离 MCP 运行检查通过 |
| P2 | 日志可能残留 Cookie/Bearer 片段，循环数组使日志处理递归失败 | 整段敏感头和相关键值脱敏，数组也参与循环检测。合成敏感字段与循环结构回归通过 |

这些修复没有改变周期“本期存在合格手动挑战记录即完成”的产品语义，不要求满星或全奖励；公共资料仍不能写入个人完成状态。

## 维护流程调整

1. 维护端读取当前契约、完整目标清单和已脱敏观察，找出缺失、变化与冲突。完整范围核查仍保留，避免增量优化漏掉新活动。
2. Codex 复用有效证据，只对需要判断的事实补充研究；按当前目标一次提交差异。无变化只记录核查结果，不重写每一行。
3. 仓库清单用 `pnpm build` 后的 `pnpm catalog:check` 检查，也可 `--input <文件>`。它调用实际消费器在内存数据库中整批验证协议、身份、层级和事务；不需要启动应用或访问玩家库。
4. 新增 `verify.yml`，后续 PR 和 main 推送运行测试、构建与清单校验。该工作流仅在仓库准备好，本轮未推送、未在 GitHub 执行。
5. 维护 Skill 从重复规范改为流程入口，实时契约负责字段细节；旧领取空结果的错误处理已经移除。安装在 Codex 缓存中的旧 Skill 不会因为仓库文件修改而自动更新。

这是共享校验和现有流程收敛。本轮没有引入云服务、个人语义复核、逐条模型写库或新的目录所有者，也不宣称未经计时对比的提速倍数。

## 仍需区分的能力与限制

- **真实接口证据范围：** 本轮使用仓库已有样本和故障样本，没有登录真实账号逐玩法打关验证。无可靠期次字段的接口仍无法仅凭一份响应证明它不是当前期的缓存；空窗和可用时间边界已防护，不能声称穷尽全部上游响应形态。遇到新形态应补脱敏样本和确定性解析规则，不能改成模型日常裁决。
- **无截止时间的活动：** 无时间不等于常驻。已经证实限时且当前开放的内容可作为维护例外候选，但现行 v1 协议仍要求绝对窗口；本轮没有伪造时间使其入库，也没有宣称客户端已支持“截止时间待确认”。
- **规则与例外发布：** 固定锚点算法已经能保留空窗，但当前协议不能热更新新规则算法、排入未来一期例外或表示日期精度/开服条件。相关 v2 设计保留在原草案中，需要连同兼容消费能力实施；不能仅改 Skill 就认为旧客户端支持。
- **维护独立性：** 新 CLI 的清单验证已独立于玩家应用。完整研究任务队列仍使用现有 MCP 和应用工作流，尚未迁移成独立任务服务；应用退出后的任务恢复不得宣称已全面改造。
- **交付边界：** 本地源码、开发态 Electron、构建入口通过不等于已安装客户端或线上 Release 已升级。未进行本轮安装包发布、线上附件下载核验或正式数据库迁移。软件版本仍为 1.1.1；正式交付需使用另行明确批准的版本。
